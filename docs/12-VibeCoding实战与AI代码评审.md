# OpsMind · Vibe Coding 实战与 AI 代码评审

> 本文件回答面试最容易被追问的一件事：**"这项目你用了多少 AI？AI 写的代码你怎么保证质量？"**
> 立场：**设计、契约、验收由我主导；编码由 AI 生成；我负责评审、定位、对齐、回归。**
> 对齐决策日志 D1–D48 与 `backend/`、`frontend/`、`tests/` 真实实现。

---

## 一、核心叙事（先背这段）

> "我把这个项目当成一次**AI 协作开发**来做的：我不是一行行手敲，而是先把设计、接口契约、字段边界定死（写在决策日志和 04-详细设计里），再让 AI 按模块生成实现；然后我按**契约对照 + 测试 + 回归**去评审。所以关键不是'用了多少 AI 写代码'，而是**我怎么保证 AI 写的东西不跑偏**——我用三层手段：契约先行、分层验收、按 diff 定位对齐。"

**一句话回答"用了多少 AI"**：编码是 AI 生成的，**设计与判断是我做的**——功能边界、接口 schema、数据结构、取舍（为什么两关不用纯 LLM、为什么知识库用 RRF）都由我定；AI 负责按契约落地；我负责验收与修复。

---

## 二、我是怎么 vibe coding 的（工作流）

```
① 设计先行（人）：在决策日志里把"怎么做/为什么"定死（D1–D48）
② 契约先行（人）：把每个模块的接口签名、入参/出参字段、表结构、状态枚举
                  提前写进 03-数据库设计 / 04-详细设计 / 05-API设计
③ 小步生成（AI）：一次只让 AI 实现一个模块（如 judgment.py / validation.py），
                  不允许多模块一起改
④ 对照验收（人）：拿 ② 的契约逐条核对 AI 产出（字段名/枚举/返回结构/异常分支）
⑤ 跑测试（机器）：pytest（见 backend/tests/），红了先定位是契约问题还是实现问题
⑥ 按块提交：一个功能一个 commit（便于回退、便于"定位刚改了什么"）
```

**关键纪律**：
- **不让 AI 自由发挥接口**——接口/字段是"合同"，AI 只填实现；
- **一次一个模块**——避免 AI 顺手改无关文件；
- **AI 产出必须过测试**——测试是"契约的可执行版本"。

## 三、AI 生成的代码怎么评审（分层验收 checklist）

我按"从外到内"的顺序看，**只重点看 AI 改动的部分，不逐行读全仓**：

### 第 0 层 · 先看"它改了什么范围"
- 期望：只改了目标模块；若改了别的文件 → 立刻警觉（AI 常"顺手重命名/顺手重构"）。
- 手段：`git status` / `git diff`（没有 git 时见 §四 的替代法）。

### 第 1 层 · 契约符合性（最重要）
- 字段名、类型、枚举值是否与 03/04/05 一致？
  - 例：`report_type` 必须是 `{success,error,timeout,empty,host_unreachable}`；`level` 必须是 `{ok,warn,crit}`（见 `app/services/judgment.py` 的 `REPORT_TYPES/LEVELS`）。
- 函数签名/返回结构是否与调用方约定一致？
- 接口路径/入参出参是否与 05-API 一致？

### 第 2 层 · 边界与异常
- 空输入、超时、异常分支有没有覆盖？
  - 例：第二关 LLM 失败必须降级 `level=unknown` 且**不阻塞报告**（`execution.py` 里 `except OpsMindError` 分支）。
- 是否有"吞异常"导致静默失败？降级是否有记录（`degradation_notes`）？

### 第 3 层 · 与设计取舍是否一致
- 例：知识库必须"勾选才查"——如果 AI 写成默认全库检索，就是违背 D48（对照 `knowledge/search.py` 的 `if not doc_ids and not allow_full_library: return []`）。
- 例：判定第一关必须"永远不走 LLM"——若 AI 在该分支调了 LLM，是硬伤。

### 第 4 层 · 测试与静态检查
- `pytest -x -v` 全绿；`ruff check` 无告警。
- 测试本身也要看：是不是"假测试"（断言太弱/只 mock 成功路径）。

### 评审话术（面试可直接说）
> "我评审 AI 代码有个固定顺序：**先看 diff 范围 → 再对契约（字段/枚举/签名）→ 再看异常分支 → 最后跑测试和 lint**。因为 AI 最容易错的三件事是：**改错字段名、漏异常分支、顺手改无关文件**，我这几层正好各自拦截。"

## 四、如何"快速定位 AI 刚改的代码"并对齐设计

### ✅ 推荐（强烈建议）：用 git 做"改动定位"
OpsMind 目前**还没有初始化 git**（`git rev-parse` 报 not a repository）。建议一上来就：
```bash
cd D:\IdeaDocs\myproject\OpsMind
git init
git add -A && git commit -m "chore: 初始化（AI 生成前的基线）"
```
之后每让 AI 改一个模块：
```bash
git status                 # 看哪些文件被动了（先确认范围没跑偏）
git diff                   # 看具体改了哪几行（重点评审对象）
git diff --staged          # 看已暂存的（准备提交的）
git add <目标文件> && git commit -m "feat: xxx"
```
- **定位"刚改的"** = `git diff` 只看未提交改动 + `git log -p -1` 看最近一次提交；
- **小步提交** 的价值：AI 改坏了，`git checkout -- <file>` 一键回退，不用翻对话找。

### 若暂时没有 git：三个替代锚点
1. **文件修改时间排序**：`Get-ChildItem -Recurse -File | Sort LastWriteTime -Descending | Select -First 20` ——先看最近被动过的文件。
2. **模块边界隔离**：一次只让 AI 动一个目录（如只改 `app/services/`），天然限定范围。
3. **AI 改动日志**：让 AI 每次改完自报"改了哪些文件、每个文件做了什么"，我按清单核对。

### 怎么"对齐自己的设计"（关键）
- **拿决策日志/详细设计当验收基线**：AI 改完，逐条比对"这段实现是否符合 Dxx 的结论"。
- **契约对照表**：字段/枚举/接口以 03/04/05 为准，不认 AI 的"我觉得"。
- **测试=可执行的契约**：契约写成测试用例，AI 改完跑测试，红了就是偏离设计的信号。
- **冲突处理**：实现与设计冲突时——先判断"是 AI 错还是设计过时"，是 AI 错就修实现，是设计该更新就回写文档（保持"文档即最新状态"）。

## 五、踩过的坑与应对（面试真实感来源）

| 坑 | 表现 | 我的应对 |
|---|---|---|
| **悄悄改无关文件** | AI 为了"顺手"重构了别的模块 | 小步生成 + `git status` 先看范围 + 只暂存目标文件 |
| **契约漂移** | 字段名/枚举被改（如 `host_unreachable` 写成 `unreachable`） | 契约先行 + 评审第 1 层对照 + 测试断言枚举 |
| **异常被吞** | 失败静默返回空、无降级记录 | 强制要求"失败必须记 `degradation_notes`"（D38 透明化），评审第 2 层查 |
| **假测试** | 测试只覆盖成功路径 | 要求补边界/失败用例；看 coverage 与断言质量 |
| **接口幻觉** | 调用了不存在的库函数/字段 | 跑起来就报错；lint + 单测 + 真实冒烟（`scripts/e2e_host.py`） |

## 六、"你（人）在 AI 协作里到底做了什么？"（面试答法）

> "我做的是 AI 做不了或不该让它做的那部分：**定需求边界、定接口契约、做技术取舍、设计评审标准、定位问题、判定'这算不算 bug'、以及在 AI 偏离设计时把它拉回来**。AI 做的是把明确的契约翻译成代码。所以这个项目我敢说'我懂每一处为什么这么设计'——因为设计本来就是我定的，AI 只是实现。"

**反问引导（把话题引到设计深度）**：
> "其实比起'用了多少 AI'，更值得聊的是我怎么定契约和取舍，比如判定为什么拆成两关、知识库为什么用 RRF 而不是纯向量——要不要展开？"

## 七、面试官可能追问（预演）

1. **"AI 写的代码你怎么信任它？"** → 契约+测试+分层评审；不信任，所以每层都要验。
2. **"测试是不是也是 AI 写的？"** → 是，但断言由我按契约定；测试是契约的可执行版本，我会检查断言强度。
3. **"你怎么保证 AI 没改坏原来的功能？"** → 小步提交 + 回归测试（`pytest`）+ diff 只看目标范围。
4. **"没有 git 怎么定位改动？"** → mtime 排序 + 模块隔离 + AI 自报改动清单（见 §四）。
5. **"你怎么知道 AI 的实现是'对的'而不只是'能跑'？"** → 对照设计的取舍去评：能跑不等于符合设计（如"勾选才查""第一关不走 LLM"这类语义约束必须逐条验）。
